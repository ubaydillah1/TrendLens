# 📐 Strict Architecture & Directory Structure Guidelines: `py-be`

This document defines the **strict architectural rules**, directory structure, code conventions, and database migration (Alembic) standards for the `py-be` service. All new features, files, and pull requests **must adhere strictly** to these guidelines.

---

## 1. 📂 Standard Directory Structure

All application source code resides inside the `app/` directory. The root directory is strictly reserved for environment configurations (`pyproject.toml`, `alembic.ini`, `.env`, container definitions).

```
py-be/
├── alembic/                         # Alembic database migrations
│   ├── versions/                    # Autogenerated migration scripts
│   └── env.py                       # Alembic environment configuration
├── alembic.ini                      # Alembic CLI configuration
├── pyproject.toml                   # Project dependencies and packaging
├── ARCHITECTURE_RULES.md            # This specification file
└── app/
    ├── __init__.py
    ├── main.py                      # FastAPI application instance & lifespan
    │
    ├── core/                        # Global configurations & infrastructure
    │   ├── __init__.py
    │   ├── config.py                # Environment variables via pydantic-settings
    │   └── database.py              # Engine, SessionLocal, Base & get_db dependency
    │
    ├── models/                      # SQLAlchemy ORM Models (Table schema)
    │   ├── __init__.py              # MUST re-export Base and ALL models for Alembic
    │   ├── base.py                  # Base class & TimestampMixin (created_at, updated_at)
    │   └── research.py              # Table models (e.g., ResearchReport, ContentIdea)
    │
    ├── schemas/                     # Pydantic Schemas (DTOs, Request & Response validation)
    │   ├── __init__.py
    │   └── research.py              # ResearchRequest, ResearchResponse, IdeaCard
    │
    ├── api/                         # Presentation Layer (HTTP Endpoints)
    │   ├── __init__.py
    │   ├── deps.py                  # Shared FastAPI Dependencies (get_db, auth)
    │   └── v1/
    │       ├── __init__.py
    │       ├── router.py            # Central v1 router aggregating all feature routers
    │       └── endpoints/
    │           ├── __init__.py
    │           ├── health.py        # /healthz endpoint
    │           └── research.py      # /api/v1/research endpoints
    │
    ├── services/                    # Business Logic Layer (Orchestrators)
    │   ├── __init__.py
    │   └── research_service.py      # Bridges API endpoints with DB & AI Agent
    │
    └── agents/                      # AI Engine (LangGraph Workflows)
        ├── __init__.py
        ├── states/                  # Graph State definitions (TypedDict / Pydantic)
        ├── nodes/                   # Individual LangGraph execution nodes
        ├── tools/                   # Tool definitions (@tool, scrapers, APIs)
        └── graphs/                  # Compiled StateGraph builders
```

## 2. 🗄️ Strict Database & Alembic Rules

1. **SQLAlchemy Models (`app/models/`):**
   * Every model **must inherit** from `TimestampMixin` (enforcing UTC `created_at` and `updated_at`).
   * Primary keys must follow a consistent strategy: either UUID v4 or autoincrementing BigInteger (`id`).
   * Table names must be **plural** and **snake_case** (e.g., `research_reports`, `content_ideas`).

2. **Alembic Model Registration Rule (`app/models/__init__.py` & `alembic/env.py`):**
   > [!IMPORTANT]
   > Whenever you create a new model file in `app/models/`, that model **MUST be imported and re-exported in `app/models/__init__.py`**.
   * If a model is not imported in `__init__.py`, Alembic **will fail to detect table changes** when running `alembic revision --autogenerate`.
   * In `alembic/env.py`, bind `target_metadata` to `Base.metadata`:
     ```python
     from app.core.database import Base
     import app.models  # Required so all models are registered in Base.metadata
     target_metadata = Base.metadata
     ```

3. **Standard Migration Workflow:**
   * Never modify the database schema directly via manual SQL or database GUIs.
   * Generate migration:
     ```bash
     uv run alembic revision --autogenerate -m "create_research_reports_table"
     ```
   * Always inspect the generated script in `alembic/versions/` before applying it.
   * Apply migration:
     ```bash
     uv run alembic upgrade head
     ```

## 3. 🛡️ Strict Separation of Concerns

* **Routers (`app/api/`) MUST NOT contain database queries or heavy AI logic:**
  * Router responsibilities are strictly limited to: Accept HTTP Request ➔ Validate via Pydantic ➔ Invoke Service ➔ Return HTTP Response.
  * ❌ *Forbidden:* Calling `db.query(Model).filter(...)` or `graph.invoke(...)` inside route handlers.
  * ✅ *Required:* Call `research_service.trigger_daily_research(db, payload)`.

* **Services (`app/services/`):**
  * The sole orchestrator layer: coordinates database persistence, calls LangGraph agents, handles transactions, and transforms domain models.

* **Agents (`app/agents/`):**
  * Strictly dedicated to AI reasoning, prompts, tool executions, and graph flow.
  * Agent logic **must be independent** of FastAPI's request lifecycle. Agents should be easily testable via CLI or standalone background worker scripts without starting an HTTP server.

## 4. 📝 Type Annotations & Coding Standards

1. **Strict Type Hints:**
   * All function parameters and return types must have explicit type annotations.
   * Use `Annotated` for FastAPI dependencies (e.g., `db: Annotated[Session, Depends(get_db)]`).
2. **Environment Variables:**
   * Never use `os.getenv("KEY")` scattered throughout the codebase.
   * All environment configurations must be centralized in `app/core/config.py` using `pydantic-settings.BaseSettings`.
3. **Pydantic Schema Naming:**
   * Inputs/Payloads: `[Feature]Create`, `[Feature]Update`, or `[Feature]Request`.
   * Outputs/DTOs: `[Feature]Response` (must include `model_config = ConfigDict(from_attributes=True)` if mapping from ORM models).

---

## 5. 🚀 Checklist for Implementing New Features

Follow this exact order when adding an entity or feature:
1. Define Request/Response Schemas in `app/schemas/`.
2. Define Database Model in `app/models/` and export it in `app/models/__init__.py`.
3. Run `alembic revision --autogenerate` and review the migration script.
4. Run `alembic upgrade head`.
5. Implement business logic in `app/services/` (and AI graphs in `app/agents/` if applicable).
6. Implement HTTP endpoints in `app/api/v1/endpoints/` and register them in `app/api/v1/router.py`.
